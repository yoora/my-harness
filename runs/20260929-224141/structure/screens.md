# 화면 구조 — 자산 등록·판매 신청·운영자 검수

실행: 20260929-224141. 근거: prd.md §6-5, §6-7, §7, §8, §9, §14 및 story-service.md. 경쟁사 참고는 research/references.md의 P1~P3이며, 허들링의 권한·검수·MVP 범위를 우선한다.

상태: 구조 명세 작성 완료. 이 문서는 실제 Figma 제작·검증 증거가 아니다. 현재 Figma MCP 제한 때문에 화면 제작 여부를 확인하지 못했으며, Figma 5개 화면과 360px 검사 증거는 별도로 필요하다.

## 공통 모델과 경계

- 화면 ID는 S1~S5로 고정한다. 기본 390×844, 360px 검증 변형은 별도다. 긴 폼·체크리스트는 세로 스크롤하며 액션이 콘텐츠를 가리지 않는다.
- 소유자는 paid 또는 seller다. paid는 비공개·멤버 공개만 선택할 수 있다. 판매 신청은 seller만 가능하며, paid→seller 승인은 기존 채널 요청 후 운영자가 수동 처리한다. 이 5개 화면에 자동 승급을 추가하지 않는다.
- 새 Asset의 visibility 기본값은 private, review_status는 draft다. 공개 범위와 검수 상태를 각각 표시한다. 비공개 저장이 공개나 판매 신청을 유발하지 않는다.
- 멤버 공개는 소유자가 명시적으로 선택하고 저장해야 적용된다. 판매 신청은 seller가 명시적으로 선택하고 신청을 제출해야 visibility=sale_requested, review_status=pending이 된다.
- sale_requested는 공개 판매 상태가 아니다. approved는 MVP 최종 검수 상태이며 for_sale로 자동 변경되지 않는다. 구매·결제·정산·판매 중·판매 중지·허들링 픽·AI 검수는 이 실행 범위에 없다.
- 모든 입력 예시는 가상 자료로 표시한다. 실제 고객정보·회사기밀·타인 파일을 샘플로 사용하지 않는다.

## S1 — 내 자산 목록

- 목적·역할: paid/seller 소유자가 자신의 자산과 신청 상태를 확인한다.
- 주요 영역: 내 자산 헤더, 새 자산 등록 CTA, 자산 목록, 빈 상태. 목록 행은 제목·유형·공개 범위·검수 상태를 분리 표시한다.
- 행동·이동: 등록→S2, 자산 선택→S3. 빈 상태에서도 등록 가능. 다른 소유자의 비공개 자산은 표시하지 않는다.
- 상태: 자료 없음 / 자료 있음. 상태 배지는 임시저장·검수 대기·수정 요청·승인됨·반려만 사용한다.
- 근거: PRD §6-5, §7-3/4; R1/R3의 목록→상세 패턴. 샘플 목록 항목과 빈 상태 문구는 AI의 화면 구성 제안이다.

## S2 — 자산 등록

- 목적·역할: paid/seller가 자신의 자산을 저장하거나 seller가 검수를 신청한다.
- 주요 영역: 뒤로가기, 제목·설명·카테고리·태그, 첨부 파일·미리보기, 사용 방법·결과 예시·도구/버전/환경, 공개 범위, 저장/신청 액션. 판매 신청일 때 제안 가격 필드를 표시한다.
- 공개 범위: 처음에는 비공개 선택. 멤버 공개 선택은 명시적 동작으로 기록한다. paid에게 판매 신청은 선택 불가 안내와 함께 표시하며 신청 액션은 제공하지 않는다. seller만 판매 신청을 선택할 수 있다.
- 행동·이동: 비공개/멤버 공개 저장→S3(draft); seller의 판매 신청 제출→S3(pending). 판매 신청 선택만으로 제출하지 않는다. 파일 오류·필수 누락 시 같은 화면에서 해당 입력을 표시한다.
- 신청 확인 문구: “운영자 검수 후 승인 상태를 확인할 수 있습니다. 승인은 판매 시작이 아닙니다.”
- 근거: PRD §6-5, §8 Asset; R1/R4/R5의 메타데이터·파일 분리. 필드 배치·제안 가격 입력 방식·검증 메시지는 AI 구성 제안이며 가격 수치는 정하지 않는다.

## S3 — 자산 상세·신청 상태

- 목적·역할: 소유자가 자산 내용·공개 범위·검수 상태·운영자 코멘트를 확인한다.
- 주요 영역: 제목과 뒤로가기, 공개 범위/검수 상태, 내용·파일·사용 방법·예시·환경, 판매 신청 가격, 운영자 검수 코멘트, 상태별 행동.
- 상태별 행동: draft→수정(S2), seller의 명시적 판매 신청(S2); pending→검수 대기 안내; revision_requested→코멘트 확인 및 수정(S2) 후 재신청; approved→“승인됨 · 판매는 아직 시작되지 않았습니다”; rejected→반려 사유 확인.
- 승인·반려 결과는 읽기 전용이다. approved 이후 편집 및 rejected 이후 재신청 정책은 PRD에 없어 이번 흐름에 추가하지 않는다.
- 근거: PRD §6-5/7, §9. 수정 요청 후 수정·재신청은 검수 루프를 구현하기 위한 AI 구성 제안이며 신청 권한은 계속 seller로 제한한다.

## S4 — 운영자 검수 목록

- 목적·역할: admin이 제출된 판매 신청을 찾아 수동 검수한다. 일반 멤버 접근 불가.
- 주요 영역: 운영자 검수 헤더, 검수 대기 목록, 제목·제출자·신청 상태·신청일, 빈 상태.
- 행동·이동: 항목 선택→S5. 목록 자체에 일괄 승인 버튼을 두지 않는다. 검수 대기가 없으면 빈 상태를 보여준다.
- 상태: 기본 pending 목록; 처리 후 결과 상태를 확인할 수 있다. 목록에서 개인정보나 첨부 본문을 불필요하게 노출하지 않는다.
- 근거: PRD §6-7/7-5. 경쟁사 내부 운영자 화면 관찰 결과가 아니라 PRD 기반 설계다. 목록 열 구성과 기본 필터는 AI 구성 제안이다.

## S5 — 운영자 검수 상세

- 목적·역할: admin이 자산·근거를 직접 읽고 필수 체크리스트로 승인·수정 요청·반려를 결정한다.
- 주요 영역: 제목·제출자·검수 상태, 자산 파일/미리보기·설명·사용법·결과 예시·환경, 제안 가격과 가격 설정/승인, 필수 체크리스트 8개, 검수 코멘트, 결정 액션.
- PRD §6-7의 필수 체크리스트(각 항목에 미확인/충족/미충족과 근거를 기록):
  1. 실제 업무에 써본 것
  2. 결과 예시가 있는 것
  3. 사용 방법이 명확한 것
  4. 초보자가 따라할 수 있는 것
  5. 특정 툴/버전/환경 조건이 적혀 있는 것
  6. 개인정보/고객정보/회사기밀이 없는 것
  7. 저작권 문제가 없는 것
  8. 구매자가 바로 써볼 수 있는 것
- 승인: 8개 모두 충족이고 가격 확인을 완료해야 활성화. 체크 기본값은 전부 미확인이다. 자동 체크·AI 승인 없음.
- 수정 요청: 코멘트 입력 후 revision_requested. 반려: 사유 입력 후 rejected. 미충족 항목을 승인으로 우회하지 않는다.
- 완료 후 S4로 복귀하며 S3에 결과와 코멘트가 표시된다. approved가 되어도 visibility는 sale_requested를 유지한다.
- 근거: PRD §6-7/14, story-service 조건 2. 체크 상태 3종·항목별 근거·전부 충족 승인·반려 사유 필수는 PRD 요구를 실행 가능하게 만든 AI 구성 제안이다. 앱의 운영자 검수와 하네스 최종 사람 승인은 별도다.

이 표는 설계 명세이며 실제 앱 권한 제어나 Figma 프로토타입 검증 결과가 아니다. 전이 ID·필드 필수 여부·화면 배치 등 추가 설계 선택은 AI 제안으로 분류한다. 판정 규칙의 단일 기준은 rules/rules.json이며 여기서 독립적인 판정 규칙 파일을 만들지 않는다.
